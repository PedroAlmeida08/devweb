Da forma em que estamos programando, as transações são criadas e destruídas após a execução de cada método.

1) Criar um entity manager (FabricadeEntityManager)
em = FabricaDeEntityManager.criarEntityManager();

Entity Manager contém uma lista dos objetos monitorados

2) Criar um objeto que cria uma transação ou recupera uma existente
tx = em.getTransaction();
Entity Manager cria a transação

3) Iniciar transação (envia um begin transaction para o SGBD)
tx.begin();
Entity Manager inicia a transação

4) Salva o objeto no BD
em.persist(umProduto);
Entity Manager verifica se o objeto é transiente (Id = null), cc, erro, pois objeto é destacado (Id != null). Id != null => objeto já inserido no BD.

Em um SGBD que usa sequence (não é o caso do MySQL - PostGRE e Oracle)
- Recupera o próximo valor da sequence
- Atribui valor ao Id
- Nesse momento o objeto passa a ser um objeto persistente (Id != null)
- Adiciona o produto à lista de objetos monitorados pelo entity manager
- Agenda a execução do comando INSERT (executado no momento do commit)

5) Commita a transação
tx.commit();

Em um SGBD que não usa sequence (MySQL)
- Executa o comando INSERT
- Atribui valor da coluna Id ao Id do objeto
- Adiciona o produto à lista de objetos monitorados pelo entity manager
- Commita

6) Retorna o Id do produto
return umProduto.getId();

7) Se a transação foi criada mas houve um erro, efetua rollback
tx.rollback();

8) Destrói o Entity Manager
em.close();

Se o Entity Manager fosse criado como variável estática e não fosse destruído:
- No momento do persist, como o objeto está salvo na lista de objetos monitorados pelo entity manager, irá tentar realizar os comandos de uptade mesmo que o objeto já tenha sido excluído => erro!

BD <-> Controller <-> Service <-> DAO

9) Executar código e cadastrar produto ("aaa", 1000, 12/12/2012);

Criação do Entity Manager é rápida, mas a criação da FabricaDeEntityManager é demorada e, por isso, há lentidão na primeira execução do código.
